# СТРАТЕГІЯ СИМЕТРИЧНОГО КРИПТОГРАФІЧНОГО ЗАХИСТУ

## «Планувальник справ»

**Версія:** 1.0  
**Дата:** 24 жовтня 2026 р.  
**Реалізація:** `crypto_store.py`, `main.py` (`AuthService`, `TodoApp`)

## 1. Що шифрується

| Дані | Чутливість | Рішення |
| --- | --- | --- |
| Задачі: `title`, `deadline`, `priority`, `remind_minutes`, `done`, `reminded` (`tasks.json`) | Найвища: опис особистих справ і розклад | **Шифруються** (AES-256-GCM), окремо для кожного профілю |
| Ключ даних (DEK) профілю (`users.json`, поле `crypto`) | Критична | Зберігається лише загорнутим (зашифрованим) під KEK |
| Ключ пристрою (`device.key`) | Критична | Файл з правами 0600, поза `tasks.json` |
| Хеш пароля для входу (`users.json`) | Висока | Не шифрується, а хешується (scrypt): має читатися до входу; файл підписано HMAC ([kontrol_tsilisnosti.md](kontrol_tsilisnosti.md)) |
| Імена профілів, ID, лічильники входу | Низька | Відкриті: потрібні екрану входу |
| Сеанс, розшифровані задачі, ключі | Критична | Лише в пам'яті, видаляються при виході |

## 2. Алгоритм і режим

- **AES-256-GCM** (AEAD, NIST SP 800-38D): забезпечує конфіденційність і цілісність одночасно; підміну шифртексту виявлено автоматично. Ключ 256 біт, тег 128 біт.
- **Nonce:** 96 біт, випадковий (`secrets`), новий при кожному шифруванні. Ліміт для випадкових nonce — 2³² шифрувань на ключ; застосунок виконує на порядки менше, а DEK ще й ротується щороку.
- **AAD** (прив'язка до контексту): `tasks|v3|<id профілю>|<версія DEK>|<номер версії даних>` для даних, `dek|v1|<id>|<версія>|<режим>` для обгортки ключа. Відро одного профілю не можна підкласти іншому.
- **KDF:** scrypt (n=2¹⁵, r=8, p=1, сіль 16 байт) для виведення KEK з пароля. Сіль **інша**, ніж у хеша для входу, інакше хеш розкривав би KEK.
- **Бібліотека:** `cryptography` (pyca). Стандартна бібліотека Python не має AES, а власна реалізація примітивів неприпустима.
- **Відхилено:** ECB (шаблони), CBC/CTR без MAC (немає цілісності), власні схеми.

## 3. Ієрархія ключів

```
пароль профілю ──scrypt──► KEK ─┐
ключ пристрою (device.key) ─────► KEK ─┤ AES-GCM (обгортка)
                                       ▼
                                 DEK профілю (256 біт, випадковий, версійований)
                                       │ AES-GCM
                                       ▼
                              відро задач профілю в tasks.json
```

- Профіль **з паролем:** KEK виводиться з пароля. Без пароля дані профілю не розшифрувати навіть маючи всі файли. Це криптографічне підкріплення правила «задачі бачить лише власник».
- Профіль **без пароля:** KEK = ключ пристрою. Захищає від витоку самого `tasks.json` (пошта, хмара, резервна копія), але не від того, хто має всю папку.
- `tasks.json` (версія 2): `{"version":2, "alg", "buckets": {"<id профілю>": {"kver", "seq", "nonce", "ct"}}}`.

## 4. Коли шифрується і розшифровується

| Момент | Дія |
| --- | --- |
| Реєстрація | Створюється DEK; загортається під KEK; записується в `users.json` |
| Вхід (після автентифікації) | Розгортається DEK; відро профілю розшифровується в пам'ять; задачі інших профілів не розшифровуються |
| Кожна зміна задачі (створення, правка, виконання, видалення, нагадування) | Відро профілю шифрується заново з новим nonce й атомарно записується |
| Вихід / автовихід | Сеанс завершується, ключі й розшифровані задачі відкидаються (`Session.end`, `service = None`) |
| Доступ до ключів | Лише через `session.keys`: у недійсному сеансі це `AccessDenied` |

Старий відкритий `tasks.json` (до версії 1.3) читається, а задачі кожного профілю шифруються при першому вході їх власника; відкритий текст зникає з файлу.

## 5. Де зберігаються ключі

| Ключ | Місце | Захист |
| --- | --- | --- |
| Пароль | Ніде | Лише хеш для входу |
| KEK | Пам'ять сеансу | Виводиться при вході |
| DEK | `users.json` (`crypto.keys`) | Загорнутий AES-GCM під KEK |
| Ключ пристрою | `device.key` поруч із програмою | Права 0600 (POSIX); не створюється мовчки наново, якщо зник |

## 6. Ротація

| Ключ | Коли | Порядок |
| --- | --- | --- |
| KEK (пароль) | Зміна, задання або зняття пароля | Нова сіль → новий KEK → DEK загортається заново. Дані не перешифровуються |
| DEK | Раз на 365 днів (перевірка при вході) або при підозрі на компрометацію | 1) нова версія DEK поруч зі старою (`users.json`); 2) перешифрування відра (`tasks.json`); 3) видалення старої версії. Збій між кроками даних не втрачає: версія DEK записана у відрі |
| Ключ пристрою | На вимогу: `python main.py --rotate-device-key`; після втрати контролю над папкою | Додається новий ключ → DEK профілів без пароля загортаються під нього → старий ключ видаляється |

## 7. Поведінка при помилках

Пошкоджений або підмінений `tasks.json`/`users.json`, неправильний ключ, відсутній `device.key` дають контрольовану помилку; файли **не перезаписуються**, дані в пам'яті не губляться. Відновлення: з резервної копії.

## 8. Обмеження

- Профіль без пароля захищений слабше: ключ лежить поруч. Рекомендовано задавати пароль. Зняття пароля повертає профіль до ключа пристрою.
- Забутий пароль = дані профілю недоступні назавжди. Втрата `device.key` = недоступні дані профілів без пароля. Копіюйте `device.key`, `users.json`, `tasks.json` разом і зберігайте окремо.
- Python не дозволяє гарантовано стерти ключі з пам'яті; захист від зловмисника з доступом до пам'яті процесу не заявляється.
- Кількість і розмір задач не приховуються. Відкат до старішої копії `tasks.json` виявляється за номером версії (див. `kontrol_tsilisnosti.md`), якщо `users.json` не відкочено разом із ним.
- Відкриті задачі старого формату лишаються у файлі, доки їх власник не увійде.
- Захист від шкідливого ПЗ, що має доступ до працюючого застосунку, поза скоупом.
