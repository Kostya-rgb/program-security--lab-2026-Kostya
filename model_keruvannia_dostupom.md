# МОДЕЛЬ КЕРУВАННЯ ДОСТУПОМ

## «Планувальник справ»

**Версія:** 1.0  
**Дата:** 24 жовтня 2026 р.  
**Реалізація:** `access_control.py` (політика), `main.py` (`TaskService`, `AuthService`)

## 1. Суб'єкти, ресурси, операції

| Суб'єкт | Опис |
| --- | --- |
| S0 Анонім | Немає активного сеансу (екран входу). |
| S1 Користувач | Активний сеанс профілю; власник свого профілю та своїх задач. |

Адміністративної ролі немає: проєкт локальний, один користувач за раз (специфікація, п. 1.2). Роль «Розробник» не діє під час роботи системи.

| Ресурс | Атрибути для рішення |
| --- | --- |
| Задача (`tasks.json`) | `owner` (ID профілю) |
| Профіль / пароль (`users.json`) | `id` |
| Сеанс (пам'ять) | `user_id`, завершено/ні, час останньої дії, ліміт неактивності |

## 2. Обрана модель

**DAC (власник ресурсу) + контекстні умови сеансу (елемент ABAC).** Політика за замовчуванням — «заборонено».

- DAC: кожна задача має єдиного власника; прав передачі й спільного доступу немає. Це точно відповідає BL-17.
- Контекст сеансу: доступ можливий лише поки сеанс активний (не завершений, не сплив ліміт неактивності). Перевіряється при кожній операції, а не лише таймером інтерфейсу.
- RBAC не потрібна: одна роль. MAC не потрібна: немає рівнів допуску й грифів конфіденційності, усі задачі одного класу.

## 3. Правила доступу

Рішення = `authorize(сеанс, дія, ресурс)` безпосередньо перед операцією. `A` — сеанс активний; `owner` — власник задачі.

| Дія | Дозволено, якщо | Інакше |
| --- | --- | --- |
| `profile:register`, `profile:login` | S0 (немає активного сеансу) | відмова |
| `profile:password` (задати/змінити/прибрати) | `A` ∧ `profile.id = session.user_id` ∧ вірний поточний пароль (якщо є) | відмова |
| `task:create` | `A`; `owner` = `session.user_id` (із введення не береться) | відмова |
| `task:list` | `A`; повертаються лише задачі з `owner = session.user_id` | відмова |
| `task:read`, `update`, `toggle`, `delete`, `remind` | `A` ∧ `task.owner = session.user_id` | відмова |
| `task:claim_legacy` (задачі без `owner`) | `A` ∧ `task.owner` відсутній ∧ `session.user_id` = перший створений профіль | відмова |
| будь-яка інша дія | ніколи | відмова |

Додатково: задача без `owner` недоступна нікому, крім випадку `claim_legacy`; чужа й неіснуюча задача дають однакову відмову (існування не розкривається); сервіс повертає копії даних, змінити їх можна лише через операції.

## 4. Реалізація

- `access_control.py`: `Session`, `AccessDenied`, таблиця `RULES`, `authorize()`, `is_allowed()`.
- `TaskService` — єдиний шлях до задач; `AuthService.change_password/login/register` викликають `authorize()` самі.
- Інтерфейс не ухвалює рішень: кнопки лише викликають сервіс; `AccessDenied` при недійсному сеансі веде на екран входу.
- Сеанс прострочений або завершений → `touch()` його не відновлює.

## 5. Перевірка

Автотести: `python -m unittest -v test_access_control` (20 сценаріїв, без GUI).

| ID | Сценарій | Очікуваний результат |
| --- | --- | --- |
| AT-22 | Власник виконує get/update/toggle/delete/remind над своєю задачею | Дозволено |
| AT-23 | Користувач A викликає ті самі операції над задачею B (навіть напряму через сервіс) | `AccessDenied`, дані B не змінено |
| AT-24 | Виклик без сеансу, із завершеним сеансом, після спливу неактивності | `AccessDenied` |
| AT-25 | Підроблені `owner`/`id`/`done` у вхідних даних | Ігноруються, `owner` = власник сеансу |
| AT-26 | Зміна пароля без сеансу або з чужим/завершеним сеансом | `AccessDenied`, пароль не змінено |
| AT-27 | `login`/`register` при активному сеансі | `AccessDenied` |
| AT-28 | Задача без `owner`; `claim_legacy` не першим профілем | Відмова / 0 перенесено |
| AT-29 | Невідома дія | `AccessDenied` (deny by default) |

## 6. Обмеження

Модель захищає від доступу через застосунок. Доступ до файлів на диску обмежує шифрування ([kryptografichnyi_zakhyst.md](kryptografichnyi_zakhyst.md)): задачі профілю з паролем нечитабельні без пароля; для профілю без пароля ключ лежить поруч, тому захист слабший.
