# 1. Призначення документа та область застосування

Цей документ є комплектом інформаційних артефактів специфікації для навчального проєкту «Планувальник справ». Його мета — зафіксувати призначення системи, правила її функціонування, зацікавлені сторони, функціональні й нефункціональні вимоги, структуру даних, варіанти використання та архітектурні погляди до початку наступних етапів розвитку програмного продукту.

За основу взято наданий програмний код. Поточна реалізація є локальним настільним застосунком на Python із графічним інтерфейсом Tkinter. Збереження задач виконується у локальному JSON-файлі tasks.json. Це означає, що вимоги [Р] нижче прямо підтверджуються реалізацією, а вимоги [П] і [В] є пропозиціями для наступних ітерацій і не видаються за вже наявні функції.

ISO/IEC/IEEE 29148:2018 визначає процеси інженерії вимог, пов’язані інформаційні елементи та рекомендації до їхнього змісту. ISO/IEC/IEEE 42010:2022 встановлює вимоги до структури та вираження опису архітектури, зокрема до використання зацікавлених сторін, їхніх проблемних питань, поглядів і представлень архітектури. На момент підготовки документа 29148:2018 залишається чинною версією, хоча для неї вже розробляється нова редакція; 42010:2022 є опублікованою редакцією 2.

## 1.2. Межі системи

До меж системи входять графічний інтерфейс, керування задачами, сортування, фільтрація виконаних задач, перевірка дедлайнів, локальні нагадування та читання/запис JSON-даних. Поза поточними межами залишаються серверна синхронізація, облікові записи користувачів, мережевий обмін, календарні інтеграції та спільна робота — у коді таких механізмів не передбачено.

# 2. Політика проєкту

Політика проєкту визначає правила, за якими повинні прийматися рішення щодо подальшої розробки «Планувальника справ». Вона потрібна для того, щоб нові функції не суперечили основним цілям, а зміни вимог залишалися керованими та перевірюваними.

## 2.1. Мета політики

Основна мета — забезпечити передбачуваний розвиток простого локального планувальника, у якому користувач може швидко зафіксувати справу, встановити строк, визначити пріоритет і отримати нагадування. Кожне нове рішення має бути пов’язане щонайменше з однією потребою користувача або технічною вимогою та мати критерій перевірки.

## 2.2. Принципи проєкту

1. Простота: нова функція не повинна ускладнювати базові операції без обґрунтованої користі.

2. Відповідність вимогам: реалізація виконується за зафіксованими та ідентифікованими вимогами.

3. Збереження даних: зміни задач повинні зберігатися локально та не втрачатися після штатного завершення програми.

4. Передбачуваність: однакові вхідні дані повинні приводити до однакового правила обробки.

5. Перевірюваність: кожна важлива вимога повинна мати критерій приймання або тестовий сценарій.

6. Розширюваність: код і модель даних мають допускати подальше додавання категорій, пошуку, статистики або резервного копіювання без руйнування базових функцій.

7. Безпека локальних даних: файл tasks.json не повинен містити зайвих персональних даних, а майбутні функції експорту/синхронізації мають бути окремо оцінені з позиції захисту інформації.

## 2.3. Ролі та відповідальність

| Роль | Відповідальність |
| --- | --- |
| Користувач | Створює та редагує задачі, визначає дедлайни, пріоритети і нагадування; перевіряє коректність відображення. |
| Розробник | Реалізує вимоги, підтримує структуру коду, перевіряє коректність збереження даних та виправляє дефекти. |

## 2.4. Політика щодо змін

Зміна вимоги реєструється як окремий запит на зміну. Для кожної зміни фіксуються ідентифікатор, причина, опис, зацікавлені сторони, залежні вимоги, вплив на дані та інтерфейс, а також рішення — прийнято, відкладено або відхилено. Після реалізації зміну необхідно перевірити за оновленими критеріями приймання.

## 2.5. Політика якості

Перевага надається коректності над кількістю функцій. Функція вважається завершеною, коли виконані визначені передумови, постумови та критерії приймання, а негативні сценарії не приводять до неконтрольованої втрати даних.

## 2.6. Політика безпеки

Для проєкту встановлюється окрема політика безпеки, оскільки дані задач зберігаються локально у `tasks.json`. Політика поширюється на код застосунку, локальне сховище, введення користувача та майбутні зміни, які можуть вплинути на конфіденційність, цілісність або доступність даних.

Повний артефакт: [politika_bezpeky.md](politika_bezpeky.md).

## 2.7. Політика конфіденційності

Проєкт є однокористувацьким і локальним. Поточна версія не передбачає облікових записів, мережевого передавання або хмарної синхронізації. Дані задач потрібні лише для функціонування планувальника та зберігаються у локальному `tasks.json`.

Повний артефакт: [politika_konfidentsiinosti.md](politika_konfidentsiinosti.md).

# 3. Опис предметної області та бізнес-цілей

Предметна область — персональне планування справ за часом. Користувач створює задачу, задає назву, дедлайн, пріоритет і режим нагадування. Після створення задача набуває статусу «невиконана». Користувач може її виконати, відредагувати або видалити. Перелік можна сортувати за дедлайном чи пріоритетом та приховувати виконані задачі.

У поточній реалізації дані задачі представлені записом словника та серіалізуються у JSON. Конкретні поля формуються під час збереження задачі: title, deadline, priority, remind_minutes, reminded, а для нової задачі також id та done.

## 3.1. Бізнес-цілі

| BG-04 | Не пропускати строки | Система перевіряє дедлайни та показує прострочені задачі; доступні нагадування. | [Р] |
| BG-05 | Швидко переглядати список | Є сортування та фільтр виконаних задач. | [Р] |
| BG-06 | Підготувати основу для розширення | Модель і правила описані так, щоб наступні функції можна було додавати керовано. | [В] |

## 3.2. Ключові зацікавлені сторони та concerns

# 4. Бізнес-логіка системи

| BL-02 | Редагування задачі | Вибрана задача завантажується у форму; після збереження її поля оновлюються, ID та факт існування задачі зберігаються. | [Р] |
| BL-03 | Зміна статусу | Поле done змінюється на протилежне значення для вибраної задачі. | [Р] |

| BL-06 | Сортування за дедлайном | Спочатку відображаються невиконані задачі, далі виконані; у кожній групі порядок визначається дедлайном. | [Р] |

| BL-08 | Позначення прострочення | Невиконана задача вважається простроченою, якщо її дедлайн менший за поточний час. | [Р] |

| BL-12 | Пошкоджений JSON | Якщо tasks.json не читається через помилку JSON або ОС, користувачу показується попередження і використовується порожній список. | [Р] |

# 8. Специфікація даних та словник даних

Сховище поточної версії — JSON-файл tasks.json. Згідно з кодом, шлях до файлу формується відносно файлу програми, а формат дати-часу визначений константою DT_FMT = "%Y-%m-%d %H:%M".

| Поле | Тип | Обов’язковість | Призначення | Приклад |
| --- | --- | --- | --- | --- |
| id | integer | так | Унікальний ідентифікатор задачі у межах локального списку. | 7 |
| title | string | так | Назва задачі. Перед збереженням обрізається пробіл по краях і не може бути порожньою. | Підготувати звіт |
| deadline | string | так | Дата і час дедлайну у форматі YYYY-MM-DD HH:MM. | 2026-10-15 18:30 |
| priority | string | так | Рівень пріоритету. | Високий |
| remind_minutes | integer/null | так | Кількість хвилин до дедлайну для нагадування. | 15 |
| reminded | boolean | так | Ознака, що нагадування вже було показано. | false |
| done | boolean | так | Статус виконання задачі. | false |

## 8.1. Інваріанти даних

1. ID задачі використовується для адресного вибору запису в інтерфейсі.

2. Поле done має логічне значення і визначає, чи вважається задача виконаною.

3. Для done=True нагадування не повинно спрацьовувати.

4. reminded=True означає, що поточне нагадування вже було показано, тому повторне спрацювання для того самого запису не відбувається.

5. deadline має відповідати формату, який розбирається datetime.strptime у застосунку.

## 8.2. Логічна схема даних

Поточна логічна структура: Tasks — масив об’єктів Task. Окремої таблиці користувачів, категорій, повторюваних правил чи журналу подій немає. У разі розширення моделі нові сутності рекомендується додавати після окремої оцінки сумісності старого JSON.

| C-05 | Формат дати й часу задається текстовим введенням і перевіряється перед збереженням. |

## 12.2. Припущення

1. Для навчальної версії використовується один локальний користувач.

2. Кількість задач є невеликою, тому JSON є достатнім базовим сховищем.

3. Користувач запускає програму на пристрої, де доступне локальне файлове сховище.

4. Системний час пристрою використовується як джерело поточного часу для дедлайнів та нагадувань.

# 13. Управління змінами вимог

Для подальшої реалізації пропонується вести простий реєстр змін. Навіть для невеликого навчального проєкту це дозволяє показати зв’язок між рішенням, вимогою, кодом і тестом.

| Поле | Зміст |
| --- | --- |
| Change ID | Унікальний номер зміни, наприклад CR-001. |
| Дата | Дата реєстрації зміни. |
| Ініціатор | Хто запропонував зміну. |
| Причина | Яку проблему або потребу вирішує зміна. |
| Зміст | Що саме змінюється у вимозі або бізнес-правилі. |
| Вплив | Зміни у UI, даних, архітектурі, тестах. |
| Рішення | Прийнято / відкладено / відхилено. |
| Пов’язані ID | BG, FR, BL, UC, AT, AR. |
| Статус реалізації | Не розпочато / у роботі / реалізовано / перевірено. |

## 13.1. Правило версій

Для першої редакції використовується версія 1.0. Зміни, що не ламають погоджену структуру, можуть отримувати номер 1.1, 1.2 тощо. Значні зміни предметної області, моделі даних або архітектури доцільно оформлювати як 2.0 після погодження впливу.

## 13.2. Мінімальний цикл зміни

1. Зареєструвати CR-XXX.

2. Описати причину та нову потребу.

3. Визначити зачеплені BG/FR/BL/UC/AR.

4. Оновити специфікацію.

5. Реалізувати зміну.

6. Додати або оновити критерії приймання.

7. Виконати перевірку та закрити зміну.
